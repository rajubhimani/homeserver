# Adding a new service to the homeserver stack

Full checklist — do all steps in the same pass, never partially (e.g. don't add a compose file without also updating the matching docs). Where a step says "check existing services for the pattern," that's deliberate — this skill teaches the mechanism, not a per-service list, since a fixed list goes stale the moment a service is added, renamed, or changed. Grep for the current state every time rather than trusting a table written here.

0a. **Before writing any image tag, env var default, or config claim, verify it against the web** — the project's own docs, GitHub releases/source, or Docker Hub/GHCR tags — via WebSearch/WebFetch. Don't rely on training-data memory for version numbers or default values; they go stale and training data can simply be wrong. This bit twice while adding `open-webui`/`ollama`: a stale image tag (`0.6.34` when `0.10.2` was current) and wrong env var defaults (`OLLAMA_MAX_LOADED_MODELS` guessed as `1`, actually `0`) both went into files before being caught. Applies to every step below that writes a version, tag, or default value — step 1's image line, step 14's "remaining env vars" block, etc.
0. **Before creating anything, check whether the service needs a port opened on the router/firewall beyond the standard `cloudflared` tunnel path.** `cloudflared` makes an outbound-only connection to Cloudflare, so any plain HTTP(S) service needs zero open inbound ports — that's the norm for this stack. A service needs an actual open port only if it speaks a non-HTTP protocol Cloudflare Tunnel's HTTP ingress can't carry (mail: SMTP/IMAP/POP3; Matrix federation: 8448; VPN: WireGuard/OpenVPN UDP; game servers; raw TCP/UDP protocols in general) or if you specifically want a non-tunneled access path (e.g. git-over-SSH). If it does, **stop and ask the user first** — name the specific port(s)/protocol and why they can't go through the tunnel, and let them decide whether that tradeoff is acceptable before you build anything. Don't silently proceed and mention it later.
1. Create `services/<service>/compose.yml`, `compose.dev.yml`, `compose.prod.yml`, `.env`, and `.env.example`.
   - `compose.yml` = base (images, env, volumes, networks — no ports). `compose.dev.yml` adds ports on all interfaces (`0.0.0.0:HOST:CONTAINER`). `compose.prod.yml` adds ports on loopback only (`127.0.0.1:HOST:CONTAINER`).
   - If the service mounts host paths or the Docker socket, also create `compose.podman.yml` with `security_opt: label=disable` (SELinux fix for Podman).
   - If it needs Postgres/MariaDB/RabbitMQ, see the `homeserver-postgres` skill first — named volume for DB data, not a bind mount.
2. Set `DATA_ROOT=../../service_data/data/<service>` (two levels up — `services/<service>/.env` to repo root) in **both** `.env` and `.env.example`. `homeserver.py` injects this automatically as an absolute path at runtime — the `.env` value is only a fallback for running `docker compose` directly.
   - **Some services have a second, independent path env var** that isn't `DATA_ROOT` (e.g. an upload/media/stacks directory under a different name) — `homeserver.py` does **not** auto-inject these; find current examples with `grep -l "=\.\./\.\./service_data/" services/*/\.env.example` and compare against each file's `DATA_ROOT=` line — any extra match is this pattern. Get the path right once; if `service_data/` is ever restructured later, grep every `.env`/`.env.example` for `=../../service_data/` or `=/.../service_data/`, not just `DATA_ROOT=` lines, or this one silently bind-mounts an empty auto-created directory instead of failing loudly.
   - **If that second root can grow large (media library, photo/video uploads, anything not just app config/db)**, it must NOT live nested inside `service_data/data/<service>/` — `backup_service()` in `homeserver.py` tars the *entire* `DATA_ROOT` directory on every `backup`/`down` (auto-snapshot), so a large secondary root nested inside it gets fully re-archived on every snapshot. Put it at its own sibling path instead, under one of the established top-level buckets — outside `service_data/data/<service>/` entirely — so it's structurally excluded from that sweep. `service_data/` has exactly four top-level buckets; don't invent a fifth (`uploads/`, `models/`, `stacks/`, etc.) — classify by what the content actually *is*, not by app-specific naming:
     - `service_data/data/<service>/` — the default. App config, small persistent state, anything DATA_ROOT-scoped. Gets backed up on every snapshot.
     - `service_data/media/<service>/` — permanent, user-facing content that's expensive or impossible to regenerate (photo/video libraries: immich, jellyfin). The defining trait is irreplaceability, not size — if it's lost, the user loses real content, not just re-download time.
     - `service_data/cache/<service>/` — regenerable content, even if large (downloaded metadata, embedding models, LLM weights). The defining trait: deleting it costs *time* (re-download/re-scan), never data.
     - `service_data/backup/<service>/` — snapshot output only, written by `backup_service()` itself. Never a service's live mount source.
     - **Exception:** a path that must be an absolute host path for docker-in-docker reasons (e.g. `dockge`'s `DOCKGE_STACKS_DIR`, which Dockge itself uses to run `docker compose` against) can't live under the relative `service_data/` scheme at all — that's a structural exception, not a fifth bucket, and doesn't get folded into `data/`/`media`/`cache` just because it's "live, non-regenerable data" by nature.
     (Confirmed real incidents, all fixed: jellyfin's `MEDIA_ROOT` nested inside `DATA_ROOT` — moved to `service_data/media/jellyfin/`; immich's `UPLOAD_LOCATION` had the same bug — moved to `service_data/media/immich/`; jellyfin's own `config/metadata/` cache (not `MEDIA_ROOT` — a separate app-populated subdirectory) — moved to `service_data/cache/jellyfin/metadata/` via a new `METADATA_ROOT` var, same fix applied to the `jellyfin-pgsql-test` instance. See `docs/services/jellyfin.md` and `docs/services/immich.md`.)
   - **This isn't only a step-1-of-a-new-service concern — it also applies to a directory an app creates on its own after the fact** (a cache dir, a downloaded-model dir, anything the app populates post-install rather than something you declared up front). If you ever notice a backup/snapshot has gotten unexpectedly large or slow, check `du`/`Get-ChildItem -Recurse` on that service's `service_data/data/<service>/` tree for exactly this pattern before assuming it's something else. (Confirmed real incident: `open-webui`'s embedding-model cache (`data/cache/`, ~1.7GB) was discovered nested this way well after the service was already running — fixed the same way, moved to `service_data/cache/open-webui/cache/` via a new `MODELS_ROOT` env var and a second bind mount over the subpath, e.g. `${MODELS_ROOT}:/app/backend/data/cache` layered on top of `${DATA_ROOT}/data:/app/backend/data`. `ollama`'s `MODELS_ROOT` follows the same `service_data/cache/<service>/` convention, updated proactively before any model data existed to migrate.)
   - **Whenever you fix this pattern — new service or retrofit alike — treat it as incomplete until all four of these land in the same pass, not as a follow-up:** (1) the compose/env change itself, (2) `.env.example` updated to match `.env` (step 3), (3) `docs/services/<service>.md`'s data-paths section documenting the new path and why it's excluded, (4) a git commit covering all of the above together. Skipping the docs step is the specific mistake that recurred on the `open-webui` fix — the code change alone looked "done" (container ran, backup shrank) but left the doc silently out of sync with reality, same failure shape step 8a warns about for reverse-proxy routes (dashboard looks fine while something real is actually missing).
3. Every env var added to `.env` must also be added to `.env.example` with its default value and a comment — they must always stay in sync.
4. If the service supports registration/signup control, add a toggle to both `.env` and `.env.example`, defaulting to **enabled**. Env var naming varies by app (`DISABLE_REGISTRATION`, `SIGNUPS_ALLOWED`, `ALLOW_SIGNUP`, etc., sometimes inverted sense) — check the app's own docs for its actual var name/values rather than guessing, and optionally scan `grep -riE "regist|signup" */.env.example` for how other services in this stack phrased the comment above theirs. Services with no public signup at all (admin-provisions-accounts-only apps) need no toggle — don't invent one.
5. Create `service_data/data/<service>/` subdirectories before first start — app data only (`mkdir -p service_data/data/<service>/app`). DB data is a named volume, so there's no `postgres/` subdirectory to create — see `homeserver-postgres` skill.
6. Add one entry to the `services` array in `services.json` (repo root) — this single entry drives both `homeserver.py`'s tier membership (`SERVICES_MIN`/`CORE`/`DAILY`/`OFFICE`/`AUTOMATION_AI`/`EXTRA`/`MANUAL`, derived from it at load time) and the landing page's card (fetched at page load — see `services/landing/index.html`'s `loadServiceData()`), so there is no second place to edit.
   - `slug` + `tier`: `"extra"` always first. Only `"core"` when explicitly asked (confirmed stable and always-on). `"daily"` for regular-use apps that don't fit a more specific opt-in grouping; `"office"` for firm/business apps (scheduling, invoicing, project/task tracking, newsletters); `"automation-ai"` for workflow/automation/AI apps — all three are opt-in tiers with the same idiom as `daily` (bootstrap lower tiers, non-cascading `down`). `"manual"` instead if it duplicates another always-on service at much higher resource cost, or should only ever start deliberately (e.g. VPN services) — never included in `up min`/`up core`/`up all` or their `down`/`restart`/`update`/`backup`/`restore` equivalents, but still a valid target for `up <service>`/`down <service>`. `down all` derives shutdown order automatically by reversing `MIN + CORE + DAILY + OFFICE + AUTOMATION_AI + EXTRA` — never maintain a separate down list.
   - If it should also get a landing-page card (almost always — the only current exceptions are `cloudflared`/`crowdsec`/`landing`/`nginx-plain`/`ollama`, infra with no direct UI), also set: `name`, `category` (`storage` | `productivity` | `dev` | `system`), `icon` (a `.card-icon` color class — reuse an existing one unless the palette genuinely needs a new color), `svg` (the icon's inner `<svg>` path data as a string, viewBox `0 0 18 18`), and `desc`. **`name` must be the actual software name** (e.g. `Forgejo`, `Guacamole`), never a generic category description (not `Password Manager`, not `Git`) — `slug`, container name, and this label all name the same truth: the specific software running there. `desc` is where the generic "what it does" text belongs. Only set `sub` if the public subdomain differs from `slug` (e.g. `firefly-importer` → `"sub": "firefly-import"`) — otherwise it's inferred automatically, so don't add a redundant `sub` that just repeats `slug`.
   - Write `desc` for a non-technical reader, not just a technical one — this stack is used by both. State what the service actually lets someone do in plain language (what jellyfin's `desc` does: "Stream movies, TV shows, and music from your own server. Netflix alternative with no subscriptions.") rather than a jargon-only fragment a non-technical person can't picture (avoid something like "Media server with transcoding"). If the service is best explained by naming its mainstream equivalent, it's fine to say so directly in `desc` itself (`"...Google Drive alternative with calendar, contacts, and more."`) — see the note on `replaces` below for why that's not redundant with the tooltip.
   - Also set `replaces` (a short string, e.g. `"Google Drive"` or `"Slack"`) if the service has a recognizable commercial/mainstream equivalent. Omit it entirely (don't set an empty string) for infra tools with no direct equivalent (Portainer, Dozzle, Airflow, Temporal, Dagster, etc.).
   - **`desc` + `replaces` is the single source of truth for the hover tooltip on all three surfaces** — the landing page card, `setup.md`'s "What's in the stack" links, and `_sidebar.md`'s matching links all show the exact same text, computed the same way: `desc`, plus a trailing `" Replaces: <replaces>."` *only if `desc` doesn't already name that product* (checked via a case-insensitive substring match on each `/`-separated alternative, e.g. `"Google Drive"` in `"...Google Drive alternative..."` — skip the suffix so it doesn't say the same thing twice). This logic lives in `services/landing/index.html`'s `buildCard()` (JS) — when hand-editing `setup.md`/`_sidebar.md` for a new service, replicate the same rule instead of just concatenating: if `desc` already mentions the replaced product, use `desc` alone as the tooltip; otherwise append the `" Replaces: X."` suffix. Never hand-author three different phrasings — compute the one tooltip string from `desc`/`replaces` and use it in all three places.
   - If this category has subgroups (currently `productivity` and `dev` — see `subcategoryLabels` at the top of `services.json` for the existing set), also set `subcategory` to the closest fit, or add a new key to `subcategoryLabels` if none fit. `storage`/`system` don't use subgroups; leave `subcategory` unset for entries in those categories. Every `category`/`subcategory` value is automatically a startable group too (`up group:<name>`, works with any action) — no extra step needed for that.
   - Array position matters for `homeserver.py`: it's what determines startup order within a tier (services start top-to-bottom). Place the new entry among its tier's existing entries, not just appended at the very end, if start order relative to specific neighbors matters (it usually doesn't).

6a. If this service has a secondary test/staging instance sharing the same card (e.g. a Postgres-backend trial running alongside the main container), don't give it its own `services.json` entry. Instead add `testSub` (and optionally `testHealth`/`testLabel`) to the main service's entry — `renderCards()` turns these into a second link on the card automatically. `testSub` is only used to build the public link URL (`https://<testSub>.<domain>`); `testHealth` is what actually gets health-checked (`/health/<testHealth>`) — **set both whenever the public subdomain and the internal container/health-route name differ** (e.g. a Jellyfin test instance was once publicly `jellyfin-test.<domain>` but its container/health route was `jellyfin-pgsql-test` — reusing one value for both caused the health check to hit a nonexistent route that silently prefix-matched an unrelated location block and reported the wrong status; see git history on `docs/services/jellyfin.md`'s "Decommissioned" section for that instance's story). If `testHealth` is omitted, it falls back to `testSub`. The landing page's `checkService()` JS auto-discovers any `testSub` on a card's data, health-checks it in parallel with the main service, and shows the card as **online** if either is up (only **offline** if both are down) — no JS changes needed, just the two data fields plus the matching `/health/<testHealth>` route from step 8.
8. Add a `/health/<service>` proxy route to **both** `services/landing/nginx.conf` and `services/landing/nginx.podman.conf` — they are two separate files covering the Docker and Podman runtimes and routinely drift out of sync; when adding or fixing a health route, check both, and while you're there diff their `location /health/` blocks (`diff <(grep -o 'location /health/[a-z-]*' services/landing/nginx.conf | sort) <(grep -o 'location /health/[a-z-]*' services/landing/nginx.podman.conf | sort)`) to catch any pre-existing drift, not just your own addition. Point at `http://<container>:<port>` — without this the landing page card always shows offline. This only feeds the dashboard's status dot — it is **not** the same as the real public route (see step 8a) and doing this alone leaves the service unreachable from a browser even though the landing page looks fine.
   - If the app validates the `Host` header, the health check can 400 forever — see `homeserver-reverse-proxy` skill's "Health check routes must set Host" section for the fix.
   - If the target has no generic `/health` route (e.g. Matrix homeservers), point at a real lightweight endpoint instead — check the app's own docs for the cheapest one available.
   - Don't assume a service that logs normally is actually reachable on the Docker network — some servers default to binding `127.0.0.1` only unless told otherwise, which looks identical to "healthy" in the container's own logs.
   - **If the service gates *every* route (including `/`) behind HTTP Basic auth** (as opposed to an app-level login page — e.g. an image like `linuxserver/firefox` where the container's own reverse proxy 401s the whole app), the health route's 401 response carries a `WWW-Authenticate: Basic` header. A same-origin `fetch()` response with that header makes the browser pop its **native login dialog on landing-page load** — this hijacks the whole dashboard, not just that one card. (Confirmed real incident: hit this on both Supabase's Kong dashboard route and `firefox`'s health route.) Fix: add `proxy_hide_header WWW-Authenticate;` to that `/health/<service>` location block (the landing page's `pingHealth()` only checks the status code, never the header, so hiding it is free) — or, if a differently-authed unprotected-enough endpoint exists (Supabase's `/rest/v1/` 401s with `WWW-Authenticate: Key`, a scheme browsers don't intercept), point at that instead. Never leave a `WWW-Authenticate: Basic`/`Digest` header reachable through `/health/*`.
8a. **Add the actual public reverse-proxy route** — a `server { listen 80; server_name <service>.${DOMAIN}; ... }` block in `services/nginx-plain/templates/default.conf.template`, proxying to `http://<container>:<port>` with `Host`/`X-Real-IP`/`X-Forwarded-For`/`X-Forwarded-Proto https` headers set (copy any existing block as a template — they're all the same shape; if the app streams over WebSocket — remote-desktop/terminal/collab tools — copy Guacamole's block instead, which adds `proxy_http_version 1.1`, `Upgrade`/`Connection: upgrade`, and a long `proxy_read_timeout`). **This is the step that actually makes `https://<service>.yourdomain.com` load** — it is easy to do steps 7–9 (landing card, health route, docs) and stop, since the dashboard will look completely correct (card shows online) while the public hostname still 502s, because nginx-plain has no `server_name` match for it and DNS/Cloudflare's wildcard record just forwards the request into that dead end.
   - **This step is not done when the file is edited — it's done when it's verified running.** `envsubst` only runs at container start, not on file change, so the template edit alone changes nothing live. Before reporting this checklist complete: `uv run homeserver.py dev restart nginx-plain` (and `landing`, if step 8's health route or its `WWW-Authenticate` handling changed), then `curl -H "Host: <service>.<domain>" http://127.0.0.1:<nginx-plain-dev-port>/` and confirm it's no longer a 502 — a real request/response, not just a config-file diff, is the actual finish line here. Writing the plan to restart-and-verify is not the same as doing it.
9. Update three index files in the same pass — all are lightweight tables/lists, not prose:
   - [`docs/11-services-reference.md`](../../../docs/11-services-reference.md): an NPM proxy host entry and a Port Reference row — **check that table first** for the next free port, then update it immediately. If the service has SSH, pick the next SSH port; never reuse a port even for manual-only services (they may run alongside `all`).
   - [`docs/10-new-services.md`](../../../docs/10-new-services.md): add a row to its per-service doc index table pointing at the new `docs/services/<service>.md` (step 10) — easy to forget since the doc file itself works fine without it, it just becomes unreachable from the index.
   - [`setup.md`](../../../setup.md): add the new service to its category/subcategory group under "What's in the stack" (bare link, purpose + replaces as the link's `title` tooltip) **and** an entry in the "Folder structure" tree listing — these are two distinct, separate spots in that file, both need the new service.
   - [`_sidebar.md`](../../../_sidebar.md) (repo root): add the same service under the matching category → subcategory branch used in `setup.md` above, **with the same `title` tooltip text** (`[Name](/docs/services/slug.md "purpose — replaces X")`) copied from the link you just added to `setup.md` — this is the docs site's persistent sidebar (see `docs/services/docs.md`), and it deliberately mirrors `setup.md`'s grouping and tooltips, so keep all three (`setup.md`, `_sidebar.md`, `services.json`'s `desc`) in sync in the same pass rather than letting them drift.
10. Create `docs/services/<service>.md` — **one consolidated doc per service**, covering purpose, port/data path, full setup walkthrough, default credentials, architecture, and every implementation gotcha/troubleshooting note in one place. This is where service-specific detail belongs — not inlined into this skill or any other.
11. Add a `healthcheck` to the service container in `compose.yml` — every service container must have one (own health endpoint where available, otherwise a simple HTTP probe or process check). This enables reliable `depends_on: condition: service_healthy` ordering and makes `docker ps` show real status. Find a worked example to copy for the new service's app type: `grep -A3 "healthcheck:" services/*/compose.yml` shows every current pattern in the stack (nginx-based static sites, HTTP apps with a `/health`-shaped endpoint, DB engines, socket-based tools, etc.) — pick whichever existing service is the closest analog rather than inventing a new shape.
12. If the service has optional sub-services (e.g. runners added via `--profile`), document them in **all** relevant doc sections in the same pass.
13. Check the service's **own documented env var/config for "behind a reverse proxy" or "force HTTPS"** — setting `X-Forwarded-Proto: https` in the proxy config is necessary but often not sufficient. See `homeserver-reverse-proxy` skill's "Always hardcode X-Forwarded-Proto: https" section for why and what else apps typically need (trusted-proxies list, force-HTTPS flag, base-URL setting, etc.).
14. **Document the image's remaining env vars for discoverability**, even ones left at their default (no behavior change). After steps 1–4 have added the vars this service actually *needs* set, check the image's own docs/`.env.example` for every other env var it supports, and append them to `services/<service>/.env.example` under a trailing comment block: `# Remaining <Service> env vars (image defaults — not previously set, no behavior change)`, one `VAR=default_value` line per var, no further commentary needed per line. This is an established convention across this stack (`grep -l "Remaining .* env vars" services/*/.env.example` shows current examples — mealie, jellyfin, forgejo, nextcloud, etc. are good templates for the comment phrasing) — it makes every tunable knob visible in one file instead of requiring a trip to upstream docs later. Don't add these to `services/<service>/.env` itself (that file should only carry vars actually acted on) or to `compose.yml`'s `environment:` block unless the default is being overridden.
15. **If several independently-deployed service directories are really one logical feature** (a "hub" — one shared login, one entry point, several sibling containers behind it; Browser Hub's five browser containers behind `browser.${DOMAIN}` is the worked example, see `docs/services/browser-hub.md`), use the **bundle** schema instead of hand-writing bash lists or special-casing the hub's slug in `homeserver.py`. This is a data-driven, fully generic mechanism — adding the *next* hub needs zero Python changes, only `services.json` fields:
    - Each member service's entry gets `"bundle": "<hub-slug>"`.
    - The hub's own entry gets `"virtual": true` (it has a landing-page card but no `services/<hub-slug>/compose.yml` of its own — it's a name standing in for its members, not a startable directory) and, if it needs extra infra that isn't itself a member (Browser Hub needs `nginx-plain`), `"requires": [...]`.
    - `homeserver.py` derives `BUNDLE_MEMBERS`/`BUNDLE_REQUIRES` from those fields automatically and makes the bare hub slug (`up <hub-slug>`, not just `up group:<hub-slug>`) expand to every member — see the block right after `CATEGORY_SUBGROUPS` in `homeserver.py`.
    - **`requires` is up-only, by design** — spliced into the expansion only for `up`/`precreate`, never `down`/`restart`/`update`/`backup`/`restore`/`dump`. A `requires` entry is typically *shared* infra (nginx-plain serves the whole stack, not just this one hub) — `down <hub-slug>` must never take down something else's dependency along with it. (Confirmed real incident: this shipped once without the split, and `down browser` stopped `nginx-plain`, which would have taken every other service's public route offline too — not just the hub's own containers.)
    - If the hub's own reverse-proxy routing references a member container by hostname in `nginx-plain`'s template (e.g. `proxy_pass http://firefox:3000`), **always use the `set $upstream ...; proxy_pass $upstream;` indirection already used throughout `default.conf.template`, never a literal `proxy_pass http://<container>:<port>;`.** A literal target makes nginx resolve that hostname at *config-load time*, which fails hard (`host not found in upstream`, `nginx: [emerg]`, container won't start) if `nginx-plain` starts before that member container exists on the network — a real race, not a hypothetical one, especially likely right after `requires` brings `nginx-plain` up as part of a fresh `up <hub-slug>`. The `set $upstream` form defers resolution to request time via the file's `resolver` directive, which tolerates that ordering. (Confirmed real incident: Browser Hub's `/_status/<slug>` liveness-check locations were written with the literal form and intermittently crashed `nginx-plain` on cold start until fixed to match every other location block in the file.)
    - Give each member its own landing-page card as normal (step 6) if individual per-member status matters (Browser Hub does — see `s.path` below), or leave members cardless (no `name`/`category`/etc., just `slug`/`tier`/`bundle`) if only the hub-level card should appear.
    - **If members live at a subpath of the hub's hostname instead of their own subdomain** (`browser.${DOMAIN}/firefox/`, not `firefox.${DOMAIN}`), each member's card needs `"sub": "<hub-slug>"` (so its link uses the *hub's* subdomain, not one implied by its own slug) plus `"path": "<member-slug>/"` (trailing slash — nginx's `location /<member-slug>/ { ... }` blocks are prefix matches that require it, a link missing it 404s). `services/landing/index.html`'s `buildCard()` builds the link as `https://${sub}.${DOMAIN}/${path}` when `s.path` is present. The hub's own card needs **neither field** — its slug already equals the hub's subdomain, so the plain default (`https://${sub}.${DOMAIN}`) is already correct; giving it a `path` too is the bug that shipped once (produced `https://${DOMAIN}/browser` — the bare apex domain, which has no such route at all — instead of `https://browser.${DOMAIN}`) before this was corrected.
