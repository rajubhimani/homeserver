# Adding a new service to the homeserver stack

Full checklist — do all steps in the same pass, never partially (e.g. don't add a compose file without also updating the matching docs). Where a step says "check existing services for the pattern," that's deliberate — this skill teaches the mechanism, not a per-service list, since a fixed list goes stale the moment a service is added, renamed, or changed. Grep for the current state every time rather than trusting a table written here.

0a. **Before writing any image tag, env var default, or config claim, verify it against the web** — the project's own docs, GitHub releases/source, or Docker Hub/GHCR tags — via WebSearch/WebFetch. Don't rely on training-data memory for version numbers or default values; they go stale and training data can simply be wrong. This bit twice while adding `open-webui`/`ollama`: a stale image tag (`0.6.34` when `0.10.2` was current) and wrong env var defaults (`OLLAMA_MAX_LOADED_MODELS` guessed as `1`, actually `0`) both went into files before being caught. Applies to every step below that writes a version, tag, or default value — step 1's image line, step 14's "remaining env vars" block, etc.
0. **Before creating anything, check whether the service needs a port opened on the router/firewall beyond the standard `cloudflared` tunnel path.** `cloudflared` makes an outbound-only connection to Cloudflare, so any plain HTTP(S) service needs zero open inbound ports — that's the norm for this stack. A service needs an actual open port only if it speaks a non-HTTP protocol Cloudflare Tunnel's HTTP ingress can't carry (mail: SMTP/IMAP/POP3; Matrix federation: 8448; VPN: WireGuard/OpenVPN UDP; game servers; raw TCP/UDP protocols in general) or if you specifically want a non-tunneled access path (e.g. git-over-SSH). If it does, **stop and ask the user first** — name the specific port(s)/protocol and why they can't go through the tunnel, and let them decide whether that tradeoff is acceptable before you build anything. Don't silently proceed and mention it later.
1. Create `<service>/compose.yml`, `compose.dev.yml`, `compose.prod.yml`, `.env`, and `.env.example`.
   - `compose.yml` = base (images, env, volumes, networks — no ports). `compose.dev.yml` adds ports on all interfaces (`0.0.0.0:HOST:CONTAINER`). `compose.prod.yml` adds ports on loopback only (`127.0.0.1:HOST:CONTAINER`).
   - If the service mounts host paths or the Docker socket, also create `compose.podman.yml` with `security_opt: label=disable` (SELinux fix for Podman).
   - If it needs Postgres/MariaDB/RabbitMQ, see the `homeserver-postgres` skill first — named volume for DB data, not a bind mount.
2. Set `DATA_ROOT=../service_data/data/<service>` in **both** `.env` and `.env.example`. `homeserver.py` injects this automatically as an absolute path at runtime — the `.env` value is only a fallback for running `docker compose` directly.
   - **Some services have a second, independent path env var** that isn't `DATA_ROOT` (e.g. an upload/media/stacks directory under a different name) — `homeserver.py` does **not** auto-inject these; find current examples with `grep -l "=\.\./service_data/" */\.env.example` and compare against each file's `DATA_ROOT=` line — any extra match is this pattern. Get the path right once; if `service_data/` is ever restructured later, grep every `.env`/`.env.example` for `=../service_data/` or `=/.../service_data/`, not just `DATA_ROOT=` lines, or this one silently bind-mounts an empty auto-created directory instead of failing loudly.
   - **If that second root can grow large (media library, photo/video uploads, anything not just app config/db)**, it must NOT live nested inside `service_data/data/<service>/` — `backup_service()` in `homeserver.py` tars the *entire* `DATA_ROOT` directory on every `backup`/`down` (auto-snapshot), so a large secondary root nested inside it gets fully re-archived on every snapshot. Put it at its own sibling path instead, e.g. `service_data/media/<service>` or `service_data/uploads/<service>` — outside `service_data/data/<service>/` entirely — so it's structurally excluded from that sweep. (Confirmed real incident: jellyfin's `MEDIA_ROOT` was nested this way and every backup was archiving the whole movie/TV library; moved to `service_data/media/jellyfin/` — see `docs/services/jellyfin.md`. `immich`'s `UPLOAD_LOCATION` has the same bug as of this writing and hasn't been fixed yet — check before assuming it's clean.)
   - **This isn't only a step-1-of-a-new-service concern — it also applies to a directory an app creates on its own after the fact** (a cache dir, a downloaded-model dir, anything the app populates post-install rather than something you declared up front). If you ever notice a backup/snapshot has gotten unexpectedly large or slow, check `du`/`Get-ChildItem -Recurse` on that service's `service_data/data/<service>/` tree for exactly this pattern before assuming it's something else. (Confirmed real incident: `open-webui`'s embedding-model cache (`data/cache/`, ~1.7GB) was discovered nested this way well after the service was already running — fixed the same way, moved to `service_data/models/open-webui/cache/` via a new `MODELS_ROOT` env var and a second bind mount over the subpath, e.g. `${MODELS_ROOT}:/app/backend/data/cache` layered on top of `${DATA_ROOT}/data:/app/backend/data`.)
   - **Whenever you fix this pattern — new service or retrofit alike — treat it as incomplete until all four of these land in the same pass, not as a follow-up:** (1) the compose/env change itself, (2) `.env.example` updated to match `.env` (step 3), (3) `docs/services/<service>.md`'s data-paths section documenting the new path and why it's excluded, (4) a git commit covering all of the above together. Skipping the docs step is the specific mistake that recurred on the `open-webui` fix — the code change alone looked "done" (container ran, backup shrank) but left the doc silently out of sync with reality, same failure shape step 8a warns about for reverse-proxy routes (dashboard looks fine while something real is actually missing).
3. Every env var added to `.env` must also be added to `.env.example` with its default value and a comment — they must always stay in sync.
4. If the service supports registration/signup control, add a toggle to both `.env` and `.env.example`, defaulting to **enabled**. Env var naming varies by app (`DISABLE_REGISTRATION`, `SIGNUPS_ALLOWED`, `ALLOW_SIGNUP`, etc., sometimes inverted sense) — check the app's own docs for its actual var name/values rather than guessing, and optionally scan `grep -riE "regist|signup" */.env.example` for how other services in this stack phrased the comment above theirs. Services with no public signup at all (admin-provisions-accounts-only apps) need no toggle — don't invent one.
5. Create `service_data/data/<service>/` subdirectories before first start — app data only (`mkdir -p service_data/data/<service>/app`). DB data is a named volume, so there's no `postgres/` subdirectory to create — see `homeserver-postgres` skill.
6. Add the service name to `SERVICES_EXTRA` in `homeserver.py` — always extra first. Only move to `SERVICES_CORE` when explicitly asked (confirmed stable and always-on). Move to `SERVICES_MANUAL` instead if it duplicates another always-on service at much higher resource cost, or should only ever start deliberately (e.g. VPN services) — never included in `up min`/`up core`/`up all` or their `down`/`restart`/`update`/`backup`/`restore` equivalents, but still a valid target for `up <service>`/`down <service>`. `down all` derives shutdown order automatically by reversing `MIN + CORE + EXTRA` — never maintain a separate `SERVICES_DOWN` list.
7. Add a card to `landing/index.html` under the appropriate section and add its subdomain to `SERVICE_SUBDOMAINS` in the script block. **The `card-name` label must be the actual software/subdomain name** (e.g. `Forgejo`, `Guacamole`), never a generic category description (not `Password Manager`, not `Git`) — subdomain, container name, and landing-page label all name the same truth: the specific software running there. The `card-desc` text is where the generic "what it does" description belongs.
7a. If this service has a secondary test/staging instance sharing the same card (e.g. a Postgres-backend trial running alongside the main container — see `docs/services/jellyfin-pgsql-test.md` for the worked example), don't give it its own card. Instead add a second link inside the main card: `<a class="card-link-secondary" data-testsub="<public-test-subdomain>" data-testhealth="<test-container-name>"><span class="test-badge">TEST</span><span class="test-dot"></span> ...</a>`. `data-testsub` is only used to build the public link URL (`https://<data-testsub>.<domain>`); `data-testhealth` is what actually gets health-checked (`/health/<data-testhealth>`) — **keep these separate whenever the public subdomain and the internal container/health-route name differ** (e.g. Jellyfin's test link is publicly `jellyfin-test.<domain>` but its container/health route is `jellyfin-pgsql-test` — reusing one value for both caused the health check to hit a nonexistent route that silently prefix-matched an unrelated location block and reported the wrong status). If omitted, `data-testhealth` falls back to `data-testsub`. The landing page's `checkService()` JS auto-discovers any `[data-testsub]` link on a card, health-checks it in parallel with the main service, and shows the card as **online** if either is up (only **offline** if both are down) — no JS changes needed, just the markup plus the matching `/health/<data-testhealth>` route from step 8.
8. Add a `/health/<service>` proxy route to **both** `landing/nginx.conf` and `landing/nginx.podman.conf` — they are two separate files covering the Docker and Podman runtimes and routinely drift out of sync; when adding or fixing a health route, check both, and while you're there diff their `location /health/` blocks (`diff <(grep -o 'location /health/[a-z-]*' landing/nginx.conf | sort) <(grep -o 'location /health/[a-z-]*' landing/nginx.podman.conf | sort)`) to catch any pre-existing drift, not just your own addition. Point at `http://<container>:<port>` — without this the landing page card always shows offline. This only feeds the dashboard's status dot — it is **not** the same as the real public route (see step 8a) and doing this alone leaves the service unreachable from a browser even though the landing page looks fine.
   - If the app validates the `Host` header (trusted domains/allowed hosts/CSRF origin checks), a bare `proxy_pass $upstream/;` will 400 forever since it arrives with an untrusted Host — add `proxy_set_header Host localhost;` to that location block (see `docs/services/nextcloud.md`).
   - If the target has no generic `/health` route (e.g. Matrix homeservers), point at a real lightweight endpoint instead — check the app's own docs for the cheapest one available.
   - Don't assume a service that logs normally is actually reachable on the Docker network — some servers default to binding `127.0.0.1` only unless told otherwise, which looks identical to "healthy" in the container's own logs.
8a. **Add the actual public reverse-proxy route** — a `server { listen 80; server_name <service>.${DOMAIN}; ... }` block in `nginx-plain/templates/default.conf.template`, proxying to `http://<container>:<port>` with `Host`/`X-Real-IP`/`X-Forwarded-For`/`X-Forwarded-Proto https` headers set (copy any existing block as a template — they're all the same shape). **This is the step that actually makes `https://<service>.yourdomain.com` load** — it is easy to do steps 7–9 (landing card, health route, docs) and stop, since the dashboard will look completely correct (card shows online) while the public hostname still 502s, because nginx-plain has no `server_name` match for it and DNS/Cloudflare's wildcard record just forwards the request into that dead end. Restart `nginx-plain` after editing (envsubst runs at container start, not on file change) and verify with `curl -H "Host: <service>.<domain>" http://127.0.0.1:<nginx-plain-dev-port>/` before considering this done.
9. Update three index files in the same pass — all are lightweight tables/lists, not prose:
   - [`docs/11-services-reference.md`](../../../docs/11-services-reference.md): an NPM proxy host entry and a Port Reference row — **check that table first** for the next free port, then update it immediately. If the service has SSH, pick the next SSH port; never reuse a port even for manual-only services (they may run alongside `all`).
   - [`docs/10-new-services.md`](../../../docs/10-new-services.md): add a row to its per-service doc index table pointing at the new `docs/services/<service>.md` (step 10) — easy to forget since the doc file itself works fine without it, it just becomes unreachable from the index.
   - [`setup.md`](../../../setup.md): add a row to the "What's in the stack" table (service/purpose/replaces) **and** an entry in the "Folder structure" tree listing — these are two distinct, separate spots in that file, both need the new service.
10. Create `docs/services/<service>.md` — **one consolidated doc per service**, covering purpose, port/data path, full setup walkthrough, default credentials, architecture, and every implementation gotcha/troubleshooting note in one place. This is where service-specific detail belongs — not inlined into this skill or any other.
11. Add a `healthcheck` to the service container in `compose.yml` — every service container must have one (own health endpoint where available, otherwise a simple HTTP probe or process check). This enables reliable `depends_on: condition: service_healthy` ordering and makes `docker ps` show real status. Find a worked example to copy for the new service's app type: `grep -A3 "healthcheck:" */compose.yml` shows every current pattern in the stack (nginx-based static sites, HTTP apps with a `/health`-shaped endpoint, DB engines, socket-based tools, etc.) — pick whichever existing service is the closest analog rather than inventing a new shape.
12. If the service has optional sub-services (e.g. runners added via `--profile`), document them in **all** relevant doc sections in the same pass.
13. Check the service's **own documented env var/config for "behind a reverse proxy" or "force HTTPS"**. Setting `X-Forwarded-Proto: https` in the proxy config (see `homeserver-reverse-proxy` skill) is necessary but often not sufficient — many apps also need their own app-level setting confirming the original request was HTTPS (a trusted-proxies list, a `force HTTPS`/`overwriteprotocol` flag, a `ROOT_URL`/`APP_URL` the app uses to generate absolute links, etc. — naming varies a lot by app, check that app's own docs rather than guessing). Grep other services' `docs/services/*.md` for "reverse proxy" or "HTTPS" for worked examples of this class of bug if you want a concrete pattern to compare against. This class of bug causes unhealthy/503/broken-links symptoms that look unrelated to the actual cause.
14. **Document the image's remaining env vars for discoverability**, even ones left at their default (no behavior change). After steps 1–4 have added the vars this service actually *needs* set, check the image's own docs/`.env.example` for every other env var it supports, and append them to `<service>/.env.example` under a trailing comment block: `# Remaining <Service> env vars (image defaults — not previously set, no behavior change)`, one `VAR=default_value` line per var, no further commentary needed per line. This is an established convention across this stack (`grep -l "Remaining .* env vars" */.env.example` shows current examples — mealie, jellyfin, forgejo, nextcloud, etc. are good templates for the comment phrasing) — it makes every tunable knob visible in one file instead of requiring a trip to upstream docs later. Don't add these to `<service>/.env` itself (that file should only carry vars actually acted on) or to `compose.yml`'s `environment:` block unless the default is being overridden.
