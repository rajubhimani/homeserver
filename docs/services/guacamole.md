**Purpose:** Clientless remote desktop gateway — access VNC/RDP/SSH machines from any browser, no client app required.
**Port:** `8107` (host) → `8080` (container) | **Data:** `service_data/data/guacamole/` | **Requires:** Postgres | **Memory:** DB capped 384M in compose.yml; webapp/guacd: no hard limit set; measured idle ~217MB total (webapp 124 + guacd 77 + db 15 — the Tomcat webapp is the heavy part)

---

## What it is

Guacamole is a *gateway*, not a remote-desktop server. It doesn't grant access to a machine that isn't already running its own VNC or RDP service — it just lets you reach that existing service through a browser instead of a dedicated client app. Pure HTML5/WebSocket, no client install needed, and works identically over LAN (`dev`, direct IP) or your domain (`prod` + Cloudflare Tunnel) — same pattern as every other service in this stack.

## Architecture

Three containers:

- **`guacamole-db`** — Postgres, holds all connection/user data
- **`guacd`** — the protocol proxy that does the actual RDP/VNC/SSH work. Stateless, no volume needed
- **`guacamole`** — the Tomcat webapp (the UI you log into)

Deployed with `WEBAPP_CONTEXT=ROOT` so the webapp serves at `/` instead of its default `/guacamole/` subpath — this lets the landing page card and nginx proxy link straight to `guacamole.${DOMAIN}` like every other service, instead of needing an extra path segment.

## Setup

```bash
cp services/guacamole/.env.example services/guacamole/.env
# set POSTGRES_PASSWORD
uv run homeserver.py dev up guacamole
```

**The Postgres schema is not auto-migrated by the image** — it must be generated once and mounted into `/docker-entrypoint-initdb.d`. This repo's `guacamole/postgres-init/01-schema.sql` was generated by actually running the pinned image's own migration tool:

```bash
docker run --rm guacamole/guacamole:1.6.0 /opt/guacamole/bin/initdb.sh --postgresql > guacamole/postgres-init/01-schema.sql
```

**Regenerate that file if the pinned Guacamole version is ever bumped** — the schema can change between versions. `00-init.sh` (the usual ownership-grant script) must run before it alphabetically, which it does (`00-` < `01-`).

**Do not put `env_file: .env` on the `guacamole` webapp container itself** — only `guacamole-db` needs it. The webapp also recognizes the plain `POSTGRES_USER`/`POSTGRES_PASSWORD` names as deprecated aliases, and having both those (from `env_file`) and the current `POSTGRESQL_*` names (from the explicit `environment:` block) present at once makes it resolve to an empty password internally. Every login then fails with a generic "Unexpected internal error" — backend log: `PSQLException: The server requested SCRAM-based authentication, but the password is an empty string` — even though `docker exec guacamole env` shows the right value. Give the webapp only the explicit `POSTGRESQL_*` vars.

**`REMOTE_IP_VALVE_ENABLED=true` is set on the webapp** — without it, Tomcat sees every request as coming from `nginx-plain`'s own container IP (the direct TCP peer) rather than the real client, since it doesn't parse `X-Forwarded-For` by default. That breaks the login audit log and, more importantly, the brute-force-ban extension — every failure gets attributed to the shared proxy IP, so **one person's login typos can lock out everyone** behind the proxy, not just the person who mistyped. The default `internalProxies` regex already covers the `homeserver` bridge network's `172.16.0.0/12` range, so no other `REMOTE_IP_VALVE_*` var is needed. (Verified this doesn't open an IP-spoofing hole: Tomcat's `RemoteIpValve` only trusts entries appended by the actual trusted proxy chain and discards anything the client itself puts in `X-Forwarded-For`.)

**Reverse proxy needs WebSocket support** — Guacamole's client/server tunnel runs over a WebSocket connection, so `nginx-plain`'s server block for `guacamole.${DOMAIN}` needs `proxy_http_version 1.1`, `Upgrade`/`Connection: upgrade` headers, and a long `proxy_read_timeout` (set to `3600s` here) so idle remote-desktop sessions don't get the tunnel killed by the proxy.

## First login and security

Default credentials: **`guacadmin` / `guacadmin`** — baked into the schema SQL above. This is a well-known, widely-scanned-for default on internet-facing Guacamole instances, so change it immediately:

1. Log in as `guacadmin`, go to **Settings → Users → New User**
2. Set a unique username + strong password, check **"Administer system"** under Permissions, save
3. Log out, log back in as the new account to confirm full access
4. **Settings → Users → guacadmin → Delete** — removes the known-default account entirely, rather than leaving a guessable username around with just a different password

**Built-in brute-force protection**: the bundled `guacamole-auth-ban` extension bans an address for 300 seconds after 5 failed logins. This ban is tracked **in-memory only** (`InMemoryAuthenticationFailureTracker`) — if you get locked out yourself, `docker restart guacamole` clears it instantly instead of waiting out the timer.

No public signup — admin-managed only, same model as Nextcloud/Immich.

## Connecting to a target machine

Add connections under **Settings → Connections → New Connection** once logged in. What service to run on the target is platform-specific, and the two common defaults each have a real gotcha:

### Linux target running Wayland (e.g. GNOME on Fedora) — confirmed working

`x11vnc` **does not work** here — it needs a real X11 server to grab pixels from, and there isn't one under native Wayland.

1. On the target: **Settings → System → Remote Desktop** → toggle on (GUI only, no terminal). This starts `gnome-remote-desktop`'s **RDP** backend (not VNC) on port `3389`, and shows a username/password right in that panel.
2. In Guacamole: new connection, **Protocol: RDP**, hostname = target's LAN IP, port `3389`, username/password from step 1.
3. Under the connection's **Security** section, check **"Ignore server certificate"** — GNOME's RDP server presents a self-signed TLS cert with no CA behind it, and Guacamole rejects unknown certs by default.
   - Symptom if you skip this: `guacd` logs `Certificate validation failed` / `RDP server closed/refused connection: SSL/TLS connection failed (untrusted/self-signed certificate?)`.

### macOS target — known issue, no confirmed fix yet

Apple's built-in Screen Sharing uses proprietary ARD authentication that Guacamole's VNC client (`libvncclient`) cannot negotiate — even when "VNC viewers may control screen with password" is checked. This is a real, long-standing incompatibility, not a config mistake: [GUACAMOLE-1133](https://issues.apache.org/jira/browse/GUACAMOLE-1133).

- **Symptom:** `guacd` logs `ERROR: Unable to connect to VNC server` immediately, with zero RFB handshake detail even at debug log level — despite the TCP port itself being reachable (confirmed via `nc -z` from inside the `guacd` container).
- **TigerVNC is not a fix** — its macOS "server" only launches a blank virtual X11 session, not your actual desktop.
- **Documented workaround (untested in this deployment):** install **RealVNC Server** on the Mac, turn off Apple's Screen Sharing first, and set RealVNC's auth mode to **VNC Password** rather than its own cloud/account-based auth.

### Windows target

Not yet tested in this deployment, but standard Guacamole usage: enable Remote Desktop in Windows Settings → System → Remote Desktop (RDP is built in), then add a Guacamole connection with **Protocol: RDP**, port `3389`.

## Troubleshooting

**Get more detail out of `guacd`** than its default `INFO` log level shows — useful for any future connection failure:

```bash
# In services/guacamole/compose.yml, add to the guacd service:
#   environment:
#     LOG_LEVEL: debug
cd guacamole
docker compose -f compose.yml -f compose.dev.yml up -d --no-deps guacd
# reproduce the issue, then:
docker logs guacd --tail 60
# revert the compose.yml change and recreate again when done — guacd is
# stateless, so recreating it is always safe.
```

**Inspect the actual configured connection parameters** (hostname/port/etc.) directly from Postgres, if the UI values are ever in doubt:

```bash
docker exec guacamole-db psql -U guacamole -d guacamole -c "
SELECT c.connection_name, p.parameter_name, p.parameter_value
FROM guacamole_connection c
JOIN guacamole_connection_parameter p ON c.connection_id = p.connection_id
WHERE p.parameter_name IN ('hostname','port')
ORDER BY c.connection_name;
"
```

**Check real TCP reachability from guacd's own network namespace** (rules out network/firewall issues vs. protocol-level failures):

```bash
docker exec guacd sh -c 'nc -z -v -w 3 <target-ip> <port>'
```

## Migrated: `guacamole-db` from `postgres:18.4` to `postgres:18.4-alpine`

Via `uv run homeserver.py dev dump guacamole` + `dev migrate guacamole` — see `docs/services/forgejo.md`'s "Migrated: forgejo-db..." section for the full process.

**Guacamole-specific gotcha hit here:** `guacamole-db`'s `postgres-init/01-schema.sql` bootstraps the *entire* Guacamole schema on first boot (unlike forgejo's init script, which only grants permissions) — so the fresh Alpine cluster already had all the tables/types before the restore even ran, and `pg_restore` errored on every `CREATE TYPE`/`CREATE TABLE` colliding with what `initdb` had already created. This is why the restore now always runs with `--clean --if-exists`, safe here specifically because the target is always a container created fresh for the migration.
